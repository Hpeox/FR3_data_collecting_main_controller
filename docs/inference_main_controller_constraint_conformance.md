# Inference MainController Constraint Conformance

Normative source: `../../../../FR3 Inference MainController Design Constraints.md`

This matrix is maintained with the inference MainController implementation. `External` means the constraint is owned by the checked-out LeRobotFR3, SensorHub, or NUC implementation and is not changed by this package. `Blocked` identifies a concrete external contract gap rather than silently moving that ownership into MainController.

## Status summary

| Status | Meaning |
| --- | --- |
| Planned | MainController implementation or test evidence is still required. |
| Satisfied | Implemented in this package with cited evidence. |
| External satisfied | Verified in the current local external implementation. |
| External blocked | The current external implementation does not completely expose or enforce the required contract. |
| External accepted limitation | The external gap is explicit and accepted for v1; it does not block this MainController release. |
| Not applicable | An explicitly permitted option is intentionally not implemented. |

## Conformance matrix

| Constraint | Owner | Status | Implementation and test evidence |
| --- | --- | --- | --- |
| 1. MainController owns inference session, rollout, recording/bookkeeping, required workstation processes, fault classification, and termination mode | MainController | Satisfied | `inference_controller.InferenceMainController` owns these lifecycles. Its `_print()` layer reports state/ready and the first FAIL_STOP reason without teeing child logs; `run()`/`main()` preserve graceful success and propagate FAIL_STOP as a non-zero console-script exit. `test_inference_controller.py` covers repeated rollouts, recoverable abort, required-process fatal, terminal output, and exit status. Existing collection controller in `main_controller/main.py` is unchanged. |
| 1. MainController does not own SensorHub/NUC processes, policy state, or `q_reset` | Shared boundary | Satisfied | `InferenceConfig.lerobot_command()` launches only the persistent worker and passes no reset target/randomization option. There is no SensorHub/NUC managed-process entry. |
| 2. LeRobot, policy/model, `Robot::FR3`, SensorHub, FT300S, and Xense persist across rollouts | MainController / LeRobot | Satisfied | `_start_lerobot()` and the sensor processes are session-scoped; rollout methods never restart them. Successful rollout completion uses `DEMO_DONE_REQ`, while ABORT/failed cleanup uses `DEMO_DISCARD_REQ`; `STOP_REQ` is reserved for terminal session teardown. `test_repeated_explicit_rollouts_keep_one_worker` and `test_abort_discards_sensors_and_allows_another_rollout` cover persistence across repeated cycles. |
| 3. One ordinary transaction; ACK acceptance is not completion; accepted requests wait for completion STATUS; rejected requests expect no STATUS | MainController | Satisfied | `inference_protocol.ControlledClient.transact()` serializes ordinary operations and distinguishes ACK from completion STATUS; `test_inference_protocol.py` covers accepted, rejected, and concurrent callers. |
| 4. Validate inputs at receipt time; reject invalid input immediately; never defer it | MainController | Satisfied | `admit_user_action()` validates and reserves the transition under `state_lock` before handoff. Tests prove `START` and `SHUTDOWN` received during `INITIALIZING` are rejected and never queued/sent. |
| 5. LeRobot phase validation, negative ACK for new invalid requests, no ordinary queue, defensive drain only | LeRobot | External satisfied | `ControlledStrategy._validate_and_ack()` and `_transition_to()` in `LeRobotFR3/src/lerobot/rollout/strategies/controlled.py`; covered by `LeRobotFR3/tests/test_controlled_rollout.py`. |
| 6. `INITIALIZE` prepares the next rollout; MainController selects timing but never creates/passes `q_reset` | Shared boundary | Satisfied | `_initialize_rollout()` sends only `INITIALIZE`; `InferenceConfig` has no reset target. External `FR3.initialize_rollout()` owns randomization and target selection. |
| 6. NUC deterministically executes the concrete reset and does not randomize it | NUC | External satisfied | Current reverse server consumes the concrete `RESET_JOINT` target; reset randomization is absent from the NUC path. |
| 7. MainController uses LeRobot completion STATUS, never raw `RESETTING`, for `INITIALIZE` completion | MainController | Satisfied | `_initialize_rollout()` enters `READY` only after `INITIALIZED` STATUS. `test_raw_resetting_never_completes_initialize` proves FGT1 bit 0 does not change the lifecycle state. |
| 7. FR3 lower path owns `RESETTING` handshake | LeRobot / SensorHub / NUC | External satisfied | `FR3._reset_joints()` waits for `RESETTING=1` then `0`; existing focused LeRobot tests cover the handshake. |
| 8. Repeated explicit `WAIT_START -> INITIALIZE -> READY -> START -> RUNNING -> WAIT_START` cycles; no automatic reset/start | MainController | Satisfied | State transitions are command-driven. Before each explicit START, MainController captures the aligned baseline, starts FT/Xense, and requires a strictly newer ready/non-fatal aligned snapshot before rosbag and LeRobot START. Tests cover exact ordering, two successful cycles, and ABORT followed by another rollout. |
| 9. `WAIT_START` is not a NUC readiness guarantee; no v1 NUC readiness states/gate | MainController | Satisfied | `InferenceState` has no NUC readiness state and `admit_user_action('initialize')` is the explicit operator confirmation boundary. |
| 10. SensorHub remains persistent and owned by `Robot::FR3`; temporary NUC telemetry loss is recoverable without restart/epoch/SHM recreation | LeRobot / SensorHub | External satisfied | `FR3.connect()` owns SensorHub; current `SensorHubRuntime` preserves its persistent readers/caches and stops aligned publication during unavailable NUC telemetry. MainController's startup-only FT/Xense warmup lets this existing authoritative READY gate observe advancing sources, then discards the warmup acquisition without restarting SensorHub or adding another source-readiness protocol. |
| 11. SensorHub fatal surfaces through LeRobot and terminates the worker/session | LeRobot / SensorHub | External accepted limitation | `FR3._check_health()` consumes SensorHub fatal during FR3 operations, so RUNNING propagation is covered by normal observation reads. The controlled worker does not poll FR3 health while blocked in an idle control phase. An aligned `fatal` refuses the explicit startup/rollout-start gate, but MainController adds no idle polling or independent fatal supervisor and does not assume general SensorHub propagation ownership. SensorHub logs upstream attach failures and pre-READY alignment rejection on reason changes or once per second, includes per-source progress in startup timeout errors, and emits the first fatal reason once at ERROR level. Attach and alignment share one total startup deadline, while FR3 uses bounded diagnostic grace to consume the child `FATAL` reason before cleanup. The idle-phase gap remains an accepted v1 external limitation and is not a MainController implementation or release blocker. |
| 12. MainController uses aligned SHM `ready/latest_sequence/fatal` as the observation health gate and does not copy full payload | MainController | Satisfied | `AlignedHealthReader` maps only the 320-byte global header. Startup requires ready/non-fatal after LeRobot READY; every rollout captures a pre-sensor baseline and requires a strictly newer ready/non-fatal sequence before rosbag and LeRobot START; `_watchdog_loop()` continues monitoring the sequence only while RUNNING. Focused tests cover header reads, ordering, not-ready/fatal rejection, timeout rollback, and runtime stall behavior. |
| 12. Prefer a formal external header-only/read-only aligned SHM API | MainController / stable cross-process ABI | Satisfied | The intentionally isolated local `AlignedHealthReader` is the selected v1 decoupling boundary: it opens SHM read-only, pins `FR3OBS2` ABI version 2, maps only the fixed 320-byte global header, imports no LeRobot runtime module, and never copies observation payloads. `test_aligned_health_reader_reads_header_only` covers the representation. |
| 13. FGT1 fans out to SensorHub and MainController; MainController records raw telemetry and observes control flags without becoming a NUC recovery protocol | Shared boundary | Satisfied | `ZmqTelemetryReceiver` is session-persistent; FGT1 `flags` are decoded and saved in rollout `zmq_telemetry.npz`. MainController only consumes `JUMP_HOLD` as a control flag and has no NUC control/recovery API. |
| 14. User abort, `JUMP_HOLD`, aligned stall, temporary NUC telemetry loss, and manually recoverable NUC failure remain rollout recoverable | MainController | Satisfied | `request_rollout_abort()` maps these RUNNING health outcomes to `ABORT -> DEMO_DISCARD_REQ for active FT/Xense -> failed recording -> WAIT_START` without setting a session termination mode. Cleanup failure still escalates normally; absence of direct FGT1 is not independently timed out. |
| 15. RUNNING aligned sequence stall causes ABORT; MainController threshold is shorter than LeRobot max-age threshold | MainController | Satisfied | `_watchdog_loop()` admits recoverable ABORT on a stall; `InferenceConfig` rejects equal/reversed threshold ordering. `test_aligned_stall_requests_recoverable_abort` covers the path. |
| 15. LeRobot max-age watchdog is armed only in phases that need fresh observations and disarmed between rollouts | LeRobot | External satisfied | Controlled strategy calls `robot.get_observation()` only inside `_run_rollout()` and returns to blocking control waits outside RUNNING. |
| 16. `JUMP_HOLD=1` while RUNNING causes immediate recoverable abort | MainController | Satisfied | `_on_zmq_frame()` atomically reserves ABORT on robot flag bit 1. The focused test verifies failed recording and return to `WAIT_START`. |
| 17. Required process exits/fatals, LeRobot/session/policy/reset failure, and internal error are session fatal; no transparent process restart except bounded recovery of known RealSense startup fatals | MainController | Satisfied | `_on_process_fatal()` reserves the existing configured RealSense fatal patterns as a startup-only exception. `_recover_realsense_startup_if_needed()` uses `ManagedProcess.restart()` under the existing startup/termination resource lock, with `realsense_startup_max_restarts` bounding attempts; duplicate fatal lines emitted while stopping one failed launch do not consume another attempt, and each intentional restart owns its SIGINT process exit. Initial startup and every recovery generation first require four generation-scoped `RealSense Node Is Up!` lines as a launch-only gate, then require actual frames and schemas on all eight formal image topics as the authoritative usability gate before LeRobot may proceed. The 1.5-second stabilization window is not camera-health evidence. A matching fatal observed during readiness is consumed by the same bounded restart path at the next synchronous boundary. Normal startup still requires LeRobot READY and aligned SHM `ready`. Recovery/readiness failure or budget exhaustion escalates through startup failure to FAIL_STOP. RealSense fatal outside `STARTING_SERVICES`, unmatched configuration/overlay failure, unexpected exit without a pending recoverable fatal, and every other required-process fatal remain direct FAIL_STOP paths. Focused tests cover launch-only versus authoritative readiness, restart-generation log isolation, fatal during image readiness, five real restart attempts, duplicate-line/expected-exit ownership, failed recovery escalation, and unchanged Xense fatal classification. |
| 18. Normal rosbag record/stop lifecycle is allowed; recorder process recovery restart is forbidden | MainController | Satisfied | `_begin_recording()`/`_finish_recording()` use recorder services per rollout. Recorder fatal/exit uses session `FAIL_STOP`; there is no recorder process restart. |
| 19. SHUTDOWN is user-only, state-valid, non-deferred, and permits return-home; every system fault maps to no-new-motion FAIL_STOP | MainController / LeRobot | Satisfied | Admission accepts user `shutdown` in `WAIT_START`, `READY`, or `RUNNING`; RUNNING performs immediate `STOP` and recording finalization before `SHUTDOWN`. It is rejected during blocking `INITIALIZE`. Faults call `request_fail_stop()`, including KeyboardInterrupt/SIGINT and promotion of an in-progress graceful termination. A focused race test proves a later negative SHUTDOWN ACK cannot clear promoted FAIL_STOP intent. Explicit `shutdown`/`q` retains ordinary graceful admission. External worker separates `_graceful_shutdown()` return-home from `_fatal_stop()`. |
| 20. FAIL_STOP retransmits with increasing sequence until positive ACK, fatal teardown STATUS, or worker exit; ACK is not teardown completion; bounded wait/force termination follows | MainController | Satisfied | `_execute_fail_stop()` retries via fresh `ControlledClient.send()` sequences, stops delivery on the specified evidence, then `_wait_for_worker_exit()` enforces bounded exit/force-stop. The focused test requires three transmissions before ACK. |
| 21. No reset-preemption receiver requirement; FAIL_STOP may continue transmitting while synchronous reset blocks | Shared boundary | Satisfied | MainController response multiplexing and fail-stop thread do not modify LeRobot. The external worker remains single-threaded; periodic commands can wait in the transport until reset returns. |
| 22. Existing LeRobot fatal/exit is sufficient; controller disconnect is fatal; no heartbeat | Shared boundary | Satisfied | Control disconnect and worker exit are session fatal; no heartbeat was added. External `ControlledUDSDisconnected` already makes loss of the sole client fatal. |
| 23. MainController owns recording; raw FGT1 remains direct; abort consistently fails/stops recording; recording fatal escalates | MainController | Satisfied | `InferenceRolloutStore`, sensor commands, and rosbag services are MainController-owned. ACK-confirmed active-sensor bookkeeping makes partial START rollback precise. ABORT/start failure best-effort discards all active sensors and stops rosbag; one discard failure does not skip the remaining target, is recorded, and escalates into session `FAIL_STOP`. Focused tests cover partial START, aligned/rosbag/LeRobot START failures, rollback aggregation, and subsequent rollout reuse. |
| 24. Preserve termination mode/reason and required SHUTDOWN/FAIL_STOP teardown ordering | MainController | Satisfied | `termination_mode`/`termination_reason` are persisted in `session_manifest.json`; a rejected SHUTDOWN clears them only while the synchronized mode is still `SHUTDOWN`, and cannot overwrite a concurrent FAIL_STOP promotion. Sensor lifecycle operations share the existing recording lock: after startup warmup ACK, every LeRobot launch/connect/READY or aligned attach/read/not-ready/fatal failure discards all active sensors before terminal cleanup can send `STOP_REQ`. Both terminal paths wait/force LeRobot before `_stop_runtime_resources()` best-effort sends `STOP_REQ` to FT300S and Xense, closes their clients, and stops remaining dependencies. Focused tests cover concurrent startup FAIL_STOP ordering, all warmup failure stages, discard failure continuation, expected-process attribution, command-before-close ordering, and cleanup failure continuation. |
| 25. Explicit v1 non-goals remain absent | MainController | Satisfied | Final source audit found no ordinary queue, deferred command/shutdown latch, `q_reset`, NUC/SensorHub supervisor, generic restart manager, reset-preemption mechanism, raw-`RESETTING` completion, or full aligned payload read. The sole `ManagedProcess.restart()` call is the bounded RealSense startup-fatal exception recorded in constraint 17; it does not generalize to runtime or other managed processes. Focused negative tests cover the highest-risk boundaries. |
| 26. Core invariants hold together | Shared boundary | Satisfied with accepted external limitation above | MainController now warms FT/Xense only to satisfy the existing SensorHub READY contract, discards that warmup before WAIT_START, and re-arms each explicit rollout through the existing aligned header before recording or motion. FT/Xense, LeRobot, SensorHub, and all wire protocols remain persistent and unchanged; `STOP_REQ` is terminal-only. The accepted idle-phase SensorHub propagation limitation remains visible rather than being moved into MainController, and the local aligned-header representation remains intentional ABI decoupling. The FR3-owned Xense reader still strictly recognizes the two documented complete fixed layouts; MainController does not reinterpret or supervise Xense SHM. |
